ICR × SDB：LLM Agent进入生产系统的治理架构模式

|浏览量:

本文是原《Intent-Controlled Routing Pattern（ICR）》与《Stochastic-Deterministic Boundary Pattern（SDB）》两篇的合并修订版。合并的目标是消除两篇之间约一半的内容重叠（适用类型、治理分级、解决/不解决等），同时修正原文中若干边界模糊与断言过强的问题。内容由 AI 根据博主核心观点进行补充、论证、完善和改进整合而成，已经过人工审核。

ICR × SDB：LLM Agent进入生产系统的治理架构模式

TL;DR

ICR 与 SDB 共享同一个前提：LLM 不应直接调用业务系统。 在这个前提下，它们回答两个不同的问题：

  • ICR（Intent-Controlled Routing，意图控制路由）管”能力空间”：LLM 只能把自然语言翻译为结构化中间语言（IL），再由开发者定义的映射规则决定它能调度什么。这是一种表达层的能力收敛。
  • SDB（Stochastic-Deterministic Boundary，随机-确定性边界）管”单次放行”：任何要改变系统状态的行为，都必须先变成可验证的候选意图，再通过约束验证层（权限、业务规则、风险分级）才允许执行。这是一种执行层的信任校验。

两者组合使用 = 设计时收敛能力边界（ICR） + 运行时加固信任边界（SDB），构成”设计时 + 运行时”的双重防护。

需要强调的是：两个模式都不解决”AI 是否理解正确”——语义正确性是它们共同的盲区，需要单独治理（见第八部分）。

第一部分：问题的本质——Agent 时代的两个鸿沟

1.1 从传统软件到 Agent 系统

传统软件系统：

系统假设：输入经过结构化约束，程序按照确定性规则完成决策和执行。

Agent 系统：

系统发生了变化：输入不再只是数据，而是一个具有推理能力的软件主体提出的行动方案。一个具备语义理解和行动规划能力、但行为结果具有随机性的非确定性主体，开始参与系统状态变化。这同时带来了两个相互独立的问题——本文称之为”两个鸿沟”。

1.2 鸿沟一：Intent-Execution Gap（意图-执行鸿沟）

Agent 系统最大的风险，并不一定来自错误理解。更危险的是：AI 理解了目标，并提出了一个逻辑合理、但系统不应该允许执行的行动。

示例：用户说”帮我降低云服务器成本。”Agent 分析发现部分服务器利用率低，判断释放资源可以降低成本，调用 TerminateInstances(node-001, node-002)。结果生产核心节点被删除。

在这个案例中：AI 没有幻觉、目标理解正确、推理过程合理。但问题在于：合理意图 ≠ 允许执行的行为。

这就是 Intent-Execution Gap（意图-执行鸿沟）。SDB Pattern 针对的正是这个鸿沟——它解决”这个请求是否被允许“的问题。

1.3 鸿沟二：无限语言与有限系统

LLM Agent 进入生产系统，还隐含一个假设：LLM 理解需求后，可以直接决定调用业务系统的什么能力。

如果你的业务系统拥有明确的、可枚举的能力集合：

问题在于：如何确保 LLM 只调度它应该调度的能力？

这本质上是无限的自然语言表达空间与有限的确定性业务系统能力之间的映射问题。LLM 可以理解无数种表达方式，但业务系统只有有限的、确定的 API。如何在两者之间建立一座可控的桥梁，就是 ICR 要解决的根本问题——它解决”能调度什么“的问题。

1.4 统一前提：LLM 不应直接调用业务系统

两个鸿沟看似不同，但共享同一个前提：LLM 的输出不能直接成为改变系统状态的授权依据。 这也正是两篇原文合并为单一框架的原因——它们不是两套可选的方案，而是同一套治理体系中的两个正交维度。

第二部分：治理框架总览——能力边界 × 信任边界

2.1 两个模式的分工

ICR SDB
核心问题 LLM 能调度哪些能力 这次请求是否允许执行
控制对象 能力类别（能力空间） 具体请求实例（单次放行）
控制方式 映射规则（事前定义） 约束验证（运行时检查）
思维模型 “开发者控制 LLM 能调度什么” “系统验证 AI 是否被允许执行”
开发者角色 定义”IL→指令”的映射表 配置验证规则和权限策略
关键词 调度控制、映射规则、中间语言 信任边界、约束验证、安全检查

2.2 两者的真实关系：不是二元对立，而是连续谱

原文用”设计时 vs 运行时”来区分二者，这个表述在真实实现里并不成立：ICR 的”条件映射 / 拒绝映射 / 延迟映射”在运行时执行时，本身就是一种校验——它和 SDB 的”业务规则校验 / 风险分级”在功能上是高度重叠的。现实中最常见的情况，是映射规则和校验规则跑在同一个规则引擎里。

因此更准确的表述是：两者的区别不在”何时发生”，而在控制对象与校验粒度——

  • ICR 收敛”能力空间”：在表达层决定”这一类操作是否允许被表达”（例如”生产环境不允许删除用户”这一类规则，在映射层就拒绝）。
  • SDB 校验”单次请求”：在执行层决定”这个具体请求是否放行”（例如即使某类操作允许，仍要针对本次的目标对象、风险等级做判断）。

两者在一条请求链路上协作，而非互斥（见 2.4 的端到端示例）。

路径 A（放行）：

  1. ICR 翻译层生成 IL：

  3. SDB 候选意图：将指令转换为可审查对象：
  4. SDB 校验：Schema（DeleteUser 合法 ✅）→ 权限（Agent 拥有测试环境删除权限，且 Agent 权限 < 人类权限 ✅）→ 业务规则（测试环境允许删除、生产环境禁止 ✅）→ 风险（高危 → 人工审批）。
  5. 人工审批通过 → Verified Intent → 执行 UserService.DeleteUser("player_test_001") → 全程审计日志。

路径 B（拦截）：用户改口”帮我把生产环境的核心节点下线”。

  1. ICR 翻译层生成 IL：{ "operation": "TerminateInstance", "target": "node-001", "environment": "production", "reason": "降低成本" }
  2. ICR 映射层直接拒绝：命中规则 TerminateInstance AND production → 拒绝映射（不生成任何业务指令），返回拒绝原因。
  3. 即便这一层被绕过，SDB 仍会拦截：风险等级”临界”→ 禁止自动执行；业务规则”禁止下线生产核心节点”。

这个示例说明了两层各自的职责：ICR 在源头把不该出现的操作挡在表达层之外，SDB 在出口对每个具体请求做最终裁决——任意一层失守，另一层仍然兜底。

第三部分：ICR 设计——能力空间的收敛

3.1 三层架构

3.2 中间语言（IL）：格式与生成

IL 是抽象的、与具体业务系统无关的结构化表达，要求具备”结构化、确定性、可验证“三个特征。JSON Schema 是当前最主流的实现（生态成熟、LLM 结构化生成支持好、人类可读），但并非强制标准——开发者也可以选择 Protobuf、Avro 或自定义 DSL。

LLM 如何将意图翻译为指定的 IL？ 当前技术已通过结构化生成（Structured Generation）解决：

  • JSON Schema 硬约束：主流服务商（OpenAI、Anthropic）和开源生态（NVIDIA NIM）支持 guided_json、response_format 等参数，能在 Token 生成层面约束输出格式，使 LLM 无法生成枚举列表之外的词。
  • 上下文学习：在 Prompt 中提供业务系统字典和 Few-shot 示例，让翻译变成”选词填空”而非”创造”。

一个需要修正的乐观断言：原文称”格式合规率可以做到 99% 以上”。准确的说法是——在支持 token 级 constrained decoding 的服务商上可以做到很高，但严格约束可能伴随生成质量退化，且不同服务商能力差异显著。因此 ICR 不依赖 100% 的翻译准确率：格式错误或语义偏离的 IL 会被后面的映射层拦截。

3.3 映射规则层：这是”控制层”，不是”验证层”

映射规则示例：

映射规则支持五种动作：批准映射 / 拒绝映射 / 条件映射 / 部分映射 / 延迟映射（进入人工流程）。实现方式可以是静态配置（YAML/JSON）、代码式（策略模式）或可视化低代码配置。

为什么不在 Prompt 里直接写规则？ Prompt 是”建议”而映射规则是”强制”：

维度 仅用 Prompt 约束 ICR（Prompt + 映射规则）
约束性质 建议性 强制性
绕过难度 通过 Prompt 注入即可绕过 系统级，不可绕过
确定性 概率性遵守 确定性执行
可审计性 无法审计 AI 是否遵守 所有意图→指令映射均有日志
变更成本 改 Prompt、测试、上线 仅改映射规则配置，无需动 LLM

3.4 规则引擎与执行引擎分离

ICR 的映射层可以拆分为两个独立子层：规则引擎负责”决策”（这个 IL 该做什么），执行引擎负责”执行”（把决策落地为调用序列）。分离的价值：改规则不影响执行、两者可独立测试、可分别更换实现（如规则引擎从 YAML 换为数据库驱动，执行引擎从同步换为异步）。

3.5 渐进式架构：开箱即用与深度定制

普通开发者直接用业界成熟的 IL 标准即可获得”自然语言→标准 IL→业务系统”的解耦红利；高级开发者可以自定义 IL 语法与解析规则，把决定权交还给领域。

3.6 指令链编排与能力组合

ICR 不仅支持 IL 到单个指令的映射，还支持将 IL 映射为预设的”指令链”：

工程价值：原子性保证（多步操作封装为原子单元）、LLM 无需知道实现细节、指令链可完整追踪和回滚。映射输出可以是单个 API 调用、线性指令链、甚至含并行/条件分支的 DAG——开发者按业务需求自由定义。

一个粒度边界：上述校验（无论 ICR 映射还是 SDB 校验）都是”单请求”粒度的，这带来一个真实的攻击面——组合操作的复合不变量。单个 IL 可以全部合法，但组合起来非法：例如”不允许删除生产数据库”，Agent 通过”创建只读副本 → 主库改名 → 删除原库”三步完成，每一步单独校验都通过。因此”是否允许”在复合操作层面，需要会话级 / 工作流级的不变量断言（如”操作完成后主副本数 ≥ 1”），这是对单请求校验的必要补充，而不是”加一个校验插件”能覆盖的。

3.7 用指令集粒度调节 AI 自由度

指令粒度 控制方式 适用场景
细粒度指令集 暴露原子指令，允许 LLM 自由组合 高智商 Agent、探索性任务、数据分析
中粒度指令集 LLM 在预定义模板范围内编排 标准业务流程
粗粒度指令集 只暴露宏指令，LLM 只能”多选一” 高风险、强合规场景

第四部分：SDB 设计——信任边界的加固

4.1 核心原则

将 LLM 视为不可信随机输入源，而不是可信执行主体。 这里的”不可信”并非指 LLM 没有价值，而是指其输出不能直接作为改变系统状态的授权依据。

核心变化不是增加一个验证步骤，而是改变系统是否应该相信 AI 产生的行为请求。

4.2 候选意图生成层（Candidate Intent）

职责：将 LLM 输出转换为结构化、可验证的行动描述。这一层不是为了消除随机性，而是将自然语言中的模糊意图转换为系统可以审查的对象。生成后系统只获得一个候选行动，不执行。候选意图同样推荐 JSON Schema（与 IL 要求一致：”结构化、确定性、可验证”）。

4.3 约束验证层（Policy Boundary）：SDB 真正的核心

执行四类验证：

① Schema 约束：是否是合法操作？DeleteUser 是否存在？
② 权限约束：Agent 是否拥有该能力？注意 Human Permission ≠ Agent Permission——AI 默认应拥有更小权限集合。
③ 业务规则约束：例如禁止删除生产账号，允许删除测试环境账号。
④ 风险约束：根据影响决定执行路径——低风险自动执行、高风险人工审批、临界风险禁止自动执行。

四类验证均有成熟技术可复用，这一层不需要从零构建：

验证类型 可复用技术 说明
Schema 约束 JSON Schema 验证器（Ajv、Zod） API 网关层的基础能力
权限约束 RBAC/ABAC（Keycloak、Casbin） 可为 Agent 创建独立的受限权限主体
业务规则 规则引擎（Drools、Easy Rules）或配置中心（Nacos、Apollo） 支持动态热更新
风险分级 工作流/审批流引擎（Camunda、Activiti） 支持自动执行、人工审批、拦截差异化流程

约束验证层有两条边界，需要显式说明：

① 业务规则会漂移。 第一部分”降低云成本”的例子看似能靠”业务规则：禁止下线生产核心节点”拦住，但”哪台机器是核心节点”是动态信息——故障转移、扩容、负载均衡调整都会改变它。规则写死必然过期（要么漏拦、要么误拦正常的运维操作），不写死就等于没有规则。因此”业务规则约束”在动态环境里，本质是需要实时数据支撑的决策，而不是一次性写死的静态配置——落地时通常需要把”规则”与”实时上下文查询”结合起来。

② 治理配置自身必须防篡改。 整个信任边界依赖”映射规则 + 校验规则”的正确性，因此必须立一条硬性不变式：Agent 永远不能拥有治理配置的写权限（不能修改映射规则、校验规则、权限集或审批流）。这条不是可选项，而是信任边界的基石——否则高自主 Agent 理论上可以给自己放权。

4.4 确定性执行层

通过验证的对象（Verified Intent）才能进入传统业务系统执行。执行系统不需要理解 AI，它只接受已被批准的确定性命令。

一个需要修正的乐观断言：原文称”业务系统完全不需要为适配做任何改造”。准确的说法是——业务系统不需要为适配治理层做逻辑改造，但对治理而言通常仍需补齐三类工程能力：幂等（同一指令重复执行结果一致）、审计钩子（记录是谁/以什么理由发起的操作）、补偿/回滚（指令链失败时的处理）。这些与”是否为 AI 适配”无关，而是治理落地的前提。

4.5 与 Tool Calling 的关系

Tool Calling SDB
关注 调用格式 行为信任
问题 怎么调用 是否允许调用
对象 参数 意图
层级 通信协议 架构边界

很多系统认为有 Tool Calling 就解决了 Agent 安全问题，这是错误的。Tool Calling 负责”怎么调”，SDB 负责”是否允许调”，二者不是替代关系，而是不同层面的问题。

4.6 可测试性与可扩展性

可测试性：SDB 的三层结构天然支持分层测试，且核心安全逻辑（校验规则）可以在不调用任何 LLM 的情况下，用预设的候选意图数据独立测试：

组件 测试内容 难度
候选意图生成层 结构化输出是否符合 Schema 中等
约束验证层 四类校验是否按预期拦截/放行 低（纯逻辑测试）
确定性执行层 通过校验后的指令执行 低（Mock API）

可扩展性：扩展点主要在约束验证层，可像插件一样新增校验类型——合规校验（GDPR）、成本预估校验（操作成本超限拦截）、时效性校验（非工作时间高风险需审批）。新校验可独立开发、独立测试，不影响已有逻辑。

第五部分：技术可行性（两篇共用）

模块 归属 可复用技术 说明
结构化生成 ICR / SDB 共用 OpenAI、Anthropic response_format、NVIDIA NIM guided_json token 级约束；严格约束可能伴随质量退化
规则引擎 ICR / SDB 共用 Drools、QLExpress、Easy Rules 映射规则与校验规则可共用同一引擎
执行引擎 ICR / SDB 共用 Camunda（BPMN）、Temporal（高容错编排）、Airflow 指令链编排、重试、事务
Schema 验证 SDB JSON Schema（Ajv、Zod） API 网关基础能力
权限体系 SDB RBAC/ABAC（Keycloak、Casbin） 为 Agent 建独立受限主体
审批流 SDB Camunda、Activiti 自动执行 / 人工审批 / 拦截

两个模式的价值不在于发明新技术，而在于把这些成熟技术按”治理”目标重组成一个面向 LLM Agent 的框架。执行引擎通过 API 适配层把指令映射为标准 REST 调用，通过 Activity 机制保证可靠性与重试，通过信号机制处理需要等待外部反馈的长操作。

第六部分：适用 AI 类型（两篇共用）

适用性取决于一个核心变量：AI 是否具备对业务系统产生”状态变更”的能力。ICR 额外要求能力空间可预定义，SDB 则不关心能力来源。

AI 类型 ICR SDB 说明
非自主 Agent（单轮工具调用） ✅ ✅ 能力边界清晰；每次操作独立校验
受限自主 Agent（多轮、预定义工具集） ✅ ✅ 需为每轮配置映射规则；每轮请求独立校验
自主 Agent（动态生成工具） ⚠️ 需人工注册规则 ✅ 新工具须人工注册映射规则后才能调用；SDB 不关心能力来源，仍然校验
RAG Agent（只检索不操作） ❌ ❌ 不涉及状态变更，无”执行”动作
纯内容生成 ❌ ❌ 不存在执行边界 / 映射对象

对自主性的处理：ICR 要求新增能力必须人工注册映射规则后才能被调用，从根源上避免 AI 自主生成后门工具绕过管控；SDB 不介入 AI 内部的推理链（任务拆分、路径规划），只作用于”AI 试图改变外部系统状态”那一步。两者共同形成”推理自由、行动受限“的边界设计。对高自主性 AI 场景，推荐以 SDB 为主、ICR 为辅。

第七部分：治理级别（两篇共用）

两个模式都不是所有场景都需要最高安全等级。合并后的统一分级如下（每一级同时给出 ICR 映射强度与 SDB 治理链）：

级别 名称 适用场景 ICR 映射强度 SDB 治理链
L0 / P0 基础治理 内部原型、低风险工具 直接映射 Intent → Schema → Basic Policy → Execute
L1 / P1 安全治理 一般/生产系统默认 条件映射 上一级 + Permission + Business Rule + Audit
L2 / P2 严格/动态能力治理 关键业务、AI 可创建新能力 白名单严格映射 上一级 + Sandbox + Version Control + Capability Review
L3 / P3 高风险治理 金融、基础设施 审批映射 上一级 + Shadow Validation + Human Approval + Controlled Rollout

一个方向修正：渐进式上线（shadow 预演、小爆炸半径、人工兜底）不应只是 P3 级别专属，而应该是任何 Agent 首次进入生产系统的默认路径——先 shadow，用”误拦截率 + 漏放率”两个指标度量，达标后才逐步提权。P3 强调的是”长期维持的最高治理强度”，但”出生方式”应当人人如此。

第八部分：共同的盲区——语义正确性

这是两个模式共同的、最需要被正视的缺口，也是本篇合并版特别强调的部分。

Schema、权限、业务规则、风险分级四类校验能拦住”不被允许的请求“，但拦不住”被允许但语义错误的请求“。考虑一次 Prompt Injection：攻击者让 Agent 生成一个格式完全合规、能通过全部校验、但语义上是破坏性操作的候选意图（例如把”迁移数据”伪装成”删除后重建”）。此时四类校验全部通过，系统依然可能执行错误操作。

因此必须明确：ICR + SDB 治理的是”请求是否被允许”，而不是”请求是否是正确的操作”。 语义正确性需要额外的治理手段，例如：

  • Shadow / Dry-run 验证：高风险操作先在沙箱预演，对比预期结果后再放行。
  • 双模型交叉校验：高风险意图由两个独立 LLM 分别判定，不一致则拦截。
  • 目标级审批（Approval by Goal）：人类批准的是”目标”而非具体调用——由系统从目标反推具体动作，避免人在批准一个无害描述时被背后的危险调用欺骗。
  • 抽样审计与语义漂移监控：对已放行操作抽样复盘，用 embedding 相似度监控意图与实际操作的偏离。

这层治理可以视为 SDB 治理链 P3 级别中 “Shadow Validation” 的自然延伸，但值得单独成文讨论。

第九部分：解决什么，不解决什么（两篇合并）

解决：

  • Agent 能力范围可控（ICR）：开发者通过映射规则定义 LLM 能调度什么。
  • Agent 权限不失控（SDB）：合理意图也不能直接执行，必须经过校验。
  • 行为可审计：IL→指令映射 + Candidate Intent→Verified Intent 全程可追踪。
  • 随机性不进入核心系统：把随机决策限制在确定性边界之外。
  • 业务系统与 LLM 解耦：业务系统不关心请求来自人类、程序还是 LLM。
  • 防止防御性代码在业务系统中蔓延：所有约束在治理层完成，业务代码保持纯粹。

不解决：

  • LLM 的理解错误（语义正确性）：把”退款”翻译成”转账”，两个模式都不会纠正——见第八部分。
  • 业务逻辑的正确性：只控制”是否允许映射/执行”，不保证操作语义上”正确”。
  • AI 幻觉：治理层不会让 AI 变聪明。
  • 纯内容生成场景：不存在执行边界 / 映射对象。
  • 完全无边界自主 AI：如果 AI 可以修改代码、创建服务、改变系统架构，需要更高层治理。

第十部分：与业界方案的对比

本框架的独特生态位，在对比中才最清楚：

方案 控制对象 控制时机 规则由谁定义 与 ICR/SDB 的差异
Tool Calling 调用格式 生成时 LLM 只管”怎么调”，不管”是否允许”
语义路由 子代理/流程选择 生成时 LLM 路由是 AI 动态决策；ICR 是可编程映射
AI Gateway（Portkey / LiteLLM / Kong） 请求/响应 运行时 平台团队 偏网络层策略与限流，缺”意图语义”维度
OPA/Rego 策略决策 运行时 开发者 是 SDB 校验层的实现工具之一，非完整信任边界
Guardrails 框架 输入/输出 运行时 开发者 偏内容安全与格式，缺权限/审批编排
Intent-based Management 意图→策略→执行 系统运行时 系统 策略由系统决定；ICR 的策略由开发者决定
ICR 能力空间 表达层 开发者 管”能调度什么”
SDB 单次请求 执行层 开发者 管”这次是否放行”

ICR/SDB 填补的是”意图语义维度 + 权限/审批编排“这个现成网关和 guardrails 覆盖不全的部分。它们与 Tool Calling、语义路由、API 网关不是重叠关系，而是不同层面的演进。

第十一部分：治理的运维成本

治理是有代价的，必须显式讨论：

  • 审批疲劳：高风险全走人工审批，审批人容易习惯性通过，防线失效。缓解：分级审批、抽样审计、按风险动态调整阈值。
  • 误拦截率：校验过严会降低 Agent 可用性。缓解：先宽后严灰度上线、规则热更新、误拦截复盘。
  • 校验延迟：每多一层校验，多一轮规则/调用开销。缓解：规则本地化缓存、并行校验、异步审计。

只讲”怎么拦”不讲”拦的代价”，是典型的”方案视角”而非”系统视角”。治理强度（见第七部分）应当与业务风险、运维成本之间取平衡。

第十二部分：结语

两个模式的核心思想来自一个朴素的问题：

当 LLM 成为系统入口时，开发者如何确保它既足够灵活，又只做被允许的事？

答案是：把灵活性留给用户，把控制权留给开发者，把纯洁性留给业务系统。

  • ICR 通过”中间语言→映射规则→业务指令”三层结构，在设计阶段收敛 LLM 的能力空间；
  • SDB 通过”候选意图→约束验证→确定性执行”三层结构，在运行阶段对每个具体请求做最终裁决。

二者共享三个核心设计原则：

  1. 把灵活性留给用户——LLM 理解各种自然语言表达。
  2. 把控制权留给开发者——通过映射规则与校验规则决定 LLM 能做什么。
  3. 把纯洁性留给业务系统——业务代码不包含任何 AI 相关的防御逻辑。

这篇文章到底主张什么，说准确一点：本文不宣称提出了前所未有的发明，也不宣称这套框架是完整、包治百病的生产方案。它的骨架——不可信输入验证、最小权限、防腐层、审批流——都是软件工程中已被验证的思想；本文的价值在于把这些思想针对 LLM Agent 这个新语境做了一次系统化的重组，并诚实标出这套框架的边界。

这里要给一个更强的判断：这套思路不仅”成立”，而且”必要”。 任何允许 LLM Agent 影响系统状态的认真方案，都必须有”结构化意图 + 开发者规则 + 运行时校验”这一层，否则 Agent 就是在裸调业务系统。事实上，业界正在沿着这条路径收敛：各大平台的 function calling + JSON Schema 结构化输出（对应 ICR 的”LLM 只翻译、不决定”）、工具权限与可用工具集配置（对应 ICR 的映射规则层）、guardrails 与策略引擎（对应 SDB 的约束验证层）、human-in-the-loop 审批与审计（对应 SDB 的风险分级与可审计性）。本文不是在描述一条没人走过的路，而是在独立地描述出业界正在落地的那个架构形态。

但”必要”不等于”充分”。这套框架解决的是”请求是否被允许“，而不是”请求是否是正确的操作“。实体解析错误、组合操作的复合不变量、规则在动态环境中的漂移、审批的经济成本、规则的长期维护、信任边界的组织归属——这些不会被这一层自动解决，需要与语义治理、会话级校验、规则资产管理、审批经济设计和组织设计配合。这不是本文的缺陷，而是所有治理层共有的边界——没有任何单一模式是自足的。

一句话总结：ICR 管”AI 能接触什么”，SDB 管”AI 这次能不能做”——前者收敛能力空间，后者裁决单次请求，二者共同构成 LLM Agent 进入生产系统的治理边界；而”AI 是否理解正确”这个语义问题，需要在这套治理之外单独解决。
