## 根因

**TCP 是字节流，没有消息边界。**

- 连续 Send 两次，接收方可能一次收到两段拼一起（**粘包**）
- 也可能一条消息被拆成几次收到（**拆包**）
- 与 Nagle 算法、发送/接收缓冲区、MSS 分片有关

## 解决方案（自定义应用层协议）

| 方案 | 说明 |
|---|---|
| **长度前缀**（最常用） | 消息头固定字节存消息体长度 |
| 固定长度 | 每条定长，简单但不灵活 |
| 分隔符 | 如 `\n`，文本协议常用 |
| Protobuf + 长度前缀 | 二进制协议常见 |

## 接收端通用处理

1. 维护**接收缓冲区**
2. 不断追加收到的字节
3. 缓冲区 ≥ 头长度时，解析出消息长度
4. 缓冲区 ≥ 头长 + 体长时，取出完整消息
5. 剩余字节留作下一条

## 注意

- **UDP 有数据报边界，不会粘包**，但会丢包乱序
- TCP 可设 `TCP_NODELAY` 关闭 Nagle 以降低延迟（代价是包更多）

> 记忆：**粘包/拆包是 TCP 字节流的必然现象，靠"长度前缀 + 接收缓冲"解决。**
