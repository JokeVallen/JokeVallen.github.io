## 结论

事件总线用得好可以解耦模块，用不好会成为内存泄漏和重复回调的重灾区。核心不是「怎么发事件」，而是「谁订阅、什么时候退订」。

## 设计要点

| 要点 | 做法 |
|---|---|
| 类型安全 | 使用泛型 `Event<T>` 而不是字符串 key |
| 生命周期 | OnEnable 订阅，OnDisable 退订 |
| 防重复 | 订阅时去重，或使用句柄式订阅 |
| 异常隔离 | 单个订阅者异常不能中断其他订阅者 |
| 调试 | 提供事件日志与订阅者列表 |

## 常见坑

- 页面销毁后没有退订，事件中心仍持有引用
- 同一个回调重复订阅，导致执行多次
- 在事件回调里直接销毁对象，后续订阅者访问空引用
- 静态事件持有大对象或场景对象

## 推荐

UI 基类统一处理订阅与退订；业务只关心回调。复杂项目可以用 `IDisposable` 订阅句柄管理。

> 记忆：**事件总线先设计退订，再设计发布。**
